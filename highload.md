## 1. Инженерный подход к масштабированию

### 1.1 Аналогия со Сбербанком

Любую задачу масштабирования удобно рассматривать через аналогию с банковской очередью. Одно отделение, 5 операционистов, надо увеличить пропускную способность:

| Приём | Банк | IT-система |
|---|---|---|
| **Параллелизация** | Открыть ещё кассы | Горизонтальное масштабирование серверов |
| **Специализация** | Отдельные окна для разных операций | Функциональная декомпозиция |
| **Конвейер** | Сначала к операционисту, потом в кассу | Pipeline-обработка задач |
| **Очередь** | Электронная очередь с номерком | Message queue / broker |
| **Кэш** | Заранее распечатанные бланки на столе | Серверный key-value кэш |
| **Толстый клиент** | Клиент заполняет форму дома | Бизнес-логика на стороне браузера (SPA) |
| **Отложенная обработка** | «Кредит одобрим — перезвоним» | Async / deferred tasks |

**Главный урок**: инженерная задача всегда сводится к оптимизации потока данных и ресурсов. Принципы одинаковы для физического и программного мира.

### 1.2 Виды масштабирования

```
┌──────────────────────────────────────────────────────────────┐
│                    ВИДЫ МАСШТАБИРОВАНИЯ                      │
├──────────────────┬───────────────────────────────────────────┤
│  Вертикальное    │  Улучшить один сервер: CPU↑, RAM↑, SSD↑  │
│  (Scale Up)      │  Простейший первый шаг, но есть физ. лимит│
├──────────────────┼───────────────────────────────────────────┤
│  Горизонтальное  │  Добавить N одинаковых серверов            │
│  (Scale Out)     │  Требует: stateless + no SPOF + однородные│
├──────────────────┼───────────────────────────────────────────┤
│  Функциональное  │  Разные фичи → разные серверы             │
│  (Decomposition) │  Форум ≠ Новости ≠ Пользователи           │
├──────────────────┼───────────────────────────────────────────┤
│  Временное       │  Показать OK → обработать позже           │
│  (Temporal)      │  Deferred processing через очередь         │
└──────────────────┴───────────────────────────────────────────┘
```

### 1.3 Закон Амдала

Параллельное выполнение ограничено последовательными участками:

```
Ускорение = 1 / (S + (1 - S) / N)

где:
  S — доля последовательного (неразделяемого) кода
  N — количество параллельных ресурсов

Пример:
  S = 0.1 (10% кода последовательно)
  N = ∞   → максимальное ускорение = 10×
```

**Вывод**: узкие последовательные места (единственная БД, глобальный мьютекс) ограничивают всю систему независимо от числа серверов. Ищи и устраняй их в первую очередь.

### 1.4 Нефункциональные требования и профиль нагрузки

Архитектура строится не только от списка фич, а от требований к данным, нагрузке и допустимым отказам. Один и тот же функционал («пользователь пишет пост») может требовать совершенно разных решений при 100 RPS и при 100 000 RPS.

**Три группы вопросов:**

| Группа | Что выясняем | Зачем |
|---|---|---|
| **Функциональные требования** | Что умеет система, какие действия доступны | Понять доменную модель и API |
| **Профиль данных** | Сколько объектов, какой размер, как быстро растут | Оценить объём БД, кэша, индексов, трафика |
| **Нефункциональные требования** | Скорость, доступность, потери, деградация | Выбрать архитектурные паттерны и компромиссы |

**Минимальный чеклист перед проектированием:**

| Вопрос | Пример ответа | Как влияет на архитектуру |
|---|---|---|
| Средняя нагрузка | 10 000 RPS чтения | Базовая мощность backend/БД |
| Пиковая нагрузка | 100 000 RPS во время матча | Нужны кэш, CDN, очередь, деградация |
| Read/write ratio | 1000 чтений на 1 запись | Репликация и кэш дадут большой эффект |
| Размер объекта | Профиль 10 KB, фото 300 KB | Считаем storage и egress |
| Рост данных | +5 TB/месяц | Нужны партиции, шардирование, архив |
| Latency/SLO | p95 < 200 ms | Нельзя делать тяжёлые sync-операции в запросе |
| Доступность | 99.9% uptime | Нужны реплики, failover, отсутствие SPOF |
| Допустимая деградация | Можно отключить рекомендации | Планируем graceful degradation |
| Потеря данных | Сообщения терять нельзя | Нужны durable queues, транзакции, retry |
| Свежесть данных | Лайки могут отставать на 5с | Можно eventual consistency |

**Среднее ≠ максимальное.** Если сервис в среднем получает 1000 RPS, пик легко может быть 5-10× выше. Проектировать только по среднему опасно: система работает в обычный день и падает в момент, ради которого она нужна бизнесу.

**Типы нагрузки:**
- **Ровная** — проще масштабировать, достаточно запаса мощности.
- **Пиковая** — нужны кэширование, очереди, rate limit, деградация.
- **Чтение доминирует** — помогают кэш, CDN, read replicas.
- **Запись доминирует** — нужны партиционирование, батчинг, append-only/log-подходы.
- **Горячие ключи** — средняя нагрузка нормальная, но один объект перегружает шард.

**Правило архитектора**: сначала посчитать порядок величин, потом выбирать паттерн. Без чисел «нужен Kafka», «нужно шардирование» и «нужно микросервисы» — не инженерные решения, а догадки.

## 2. Трёхуровневая архитектура и кэширование

### 2.1 Трёхуровневая архитектура (3-Tier)

```
┌──────────────────────────────────────────────────────────────┐
│                         КЛИЕНТ                               │
│             (браузер / мобильное приложение)                 │
└──────────────────────┬───────────────────────────────────────┘
                       │ HTTP / WebSocket / gRPC
┌──────────────────────▼───────────────────────────────────────┐
│                    FRONTEND (Nginx)                           │
│  • Раздача статики (HTML, CSS, JS, изображения)              │
│  • Буферизация запросов (принять целиком → отдать backend-у) │
│  • SSL-терминация                                            │
│  • Базовая валидация и rate limiting                         │
│  • Балансировка нагрузки между backend-серверами             │
└──────────────────────┬───────────────────────────────────────┘
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
  ┌────────────┐ ┌────────────┐ ┌────────────┐
  │ Backend 1  │ │ Backend 2  │ │ Backend N  │
  │            │ │            │ │            │
  │ Бизнес-    │ │ Бизнес-    │ │ Бизнес-    │
  │ логика     │ │ логика     │ │ логика     │
  └──────┬─────┘ └──────┬─────┘ └──────┬─────┘
         └──────────────┼──────────────┘
                        │
┌───────────────────────▼──────────────────────────────────────┐
│                      DATABASE LAYER                           │
│              (PostgreSQL, Redis, Elasticsearch...)            │
└──────────────────────────────────────────────────────────────┘
```

**Зачем буферизация в Nginx**: backend не должен ждать медленных клиентов. Nginx принимает запрос целиком (даже с медленного мобильного соединения), только потом передаёт backend-у одним быстрым вызовом.

### 2.2 Слои кэширования

```
Запрос пользователя проходит через слои (каждый может ответить):

Browser Cache ──▶ CDN / Edge ──▶ Nginx Cache ──▶ Backend Cache (Redis) ──▶ БД
   (ETag)        (географически)  (proxy_cache)   (key-value + TTL)
```

**Принцип**: отвечай как можно раньше. Каждый слой снижает нагрузку на следующий.

**Алгоритм обращения к серверному кэшу:**
```
GET /article/42
    ↓
Проверяем Redis["article:42"]
    ├── HIT  → вернуть данные (1-3 ms)
    └── MISS → SELECT * FROM articles WHERE id=42 (50-200 ms)
               → Redis.SET("article:42", data, TTL=300)
               → вернуть данные
```

### 2.3 Стратегии инвалидации кэша

| Стратегия | Описание | Применение |
|---|---|---|
| **TTL** | Кэш протухает через N секунд | Данные, где небольшая задержка допустима |
| **Явная инвалидация** | При записи → удалить ключ из кэша | Критичные к свежести данные |
| **Write-through** | Запись одновременно в кэш и БД | Часто читаемые, редко меняющиеся |
| **Tag-based** | Версионные теги зависимостей (см. раздел 3) | Сложные зависимости блоков |

### 2.4 Проблема «Гром стада» (Thundering Herd)

```
Кэш протух одновременно для 1000 клиентов
    ↓
Все 1000 → в БД одновременно
    ↓
БД перегружена → задержки → ещё больше запросов в очереди
    ↓
Каскадный сбой
```

**Решение 1 — флаг пересчёта:**
```
GET cache[key] == null?
    └── SET cache[key + "_lock"] = true  (TTL=30с, NX — только если нет)
        ├── Успех → ты первый → пересчитай → SET cache[key] → DEL lock
        └── Неудача → другой уже считает → вернуть устаревшее значение
```

**Решение 2 — случайный TTL**: добавить ±10–20% рандомности к TTL, чтобы разные ключи протухали в разное время.

**Решение 3 — прогрев кэша (warm-up)**: перед запуском сервера/деплоем заполнить кэш топ-данными.

## 3. Линеаризация кэша и толстый клиент

### 3.1 Тегированная инвалидация кэша (Cache Linearization)

**Проблема**: страница собирается из множества блоков с разными зависимостями. При изменении пользователя надо инвалидировать все блоки, где он фигурирует — но какие именно?

**Решение — версионные теги:**

```
Каждый кэш-блок хранит список своих зависимостей:

cache["article_page:42"] = {
  html: "<html>...",
  deps: [
    {key: "article",     ver: 7},
    {key: "author:15",   ver: 3},
    {key: "comments:42", ver: 12}
  ]
}

Хранилище текущих версий (Redis):
  article_ver     = 7
  author:15_ver   = 3
  comments:42_ver = 12
```

**Процесс инвалидации при редактировании статьи:**

```
UPDATE articles SET text=... WHERE id=42
    ↓
INCR article_ver  (7 → 8)
    ↓ (никаких явных удалений кэша!)
Следующий запрос: GET cache["article_page:42"]
    ↓
Проверяем deps: article_ver должна быть 7, но сейчас 8 → MISS
    ↓
Пересчитываем страницу → сохраняем с deps[article_ver=8]
```

**Плюсы:**
- Не нужен реестр «какие кэши зависят от каких данных»
- Инвалидация ленивая (lazy) — только при следующем запросе
- Версии — простые счётчики в Redis, очень быстро

### 3.2 Толстый клиент (Thick Client / SPA)

```
                Тонкий клиент                     Толстый клиент (SPA)
┌────────────────────────────────┐    ┌────────────────────────────────┐
│ Каждое действие = полный       │    │ JS-приложение в браузере:      │
│ roundtrip к серверу            │    │ • хранит локальное состояние   │
│                                │    │ • рендерит UI сам              │
│ GET /page → сервер всё считает │    │ • ходит к серверу только за    │
│ ← HTML с данными               │    │   данными (JSON API)           │
│                                │    │                                │
│ Слой бизнес-логики — сервер    │    │ Лайк → JS сразу обновил UI    │
└────────────────────────────────┘    │ + асинхронно POST /like        │
                                      └────────────────────────────────┘
```

**Следствие**: можно показывать изменение пользователю немедленно (до ответа сервера) — это компенсирует репликационный лаг.

### 3.3 Паттерны получения данных в реальном времени

```
┌──────────────────┬───────────────────────────────────────────┐
│  Short Polling   │  Client: GET /updates каждые N секунд     │
│                  │  Просто, но N×RPS пустых ответов          │
├──────────────────┼───────────────────────────────────────────┤
│  Long Polling    │  Client: GET /updates (открыт до ~30с)    │
│  (Comet)         │  Server: держит соединение, отвечает при  │
│                  │  появлении данных или по таймауту          │
│                  │  При ответе → клиент сразу новый запрос    │
├──────────────────┼───────────────────────────────────────────┤
│  WebSocket       │  Постоянное двунаправленное соединение     │
│                  │  Низкая latency, но stateful               │
│                  │  Промежуточные прокси могут рвать связь    │
├──────────────────┼───────────────────────────────────────────┤
│  Server-Sent     │  Однонаправленный поток (сервер → клиент)  │
│  Events (SSE)    │  Проще WebSocket, работает через HTTP/1.1  │
└──────────────────┴───────────────────────────────────────────┘
```

**Адаптивный polling (exponential backoff):**
```
Нет данных 30с  → опрос каждые 1с
Нет данных 60с  → опрос каждые 5с
Нет данных 5мин → опрос каждые 30с
Есть данные     → сброс к 1с
```

### 3.4 Graceful Degradation (Плавная деградация)

**Принцип**: при перегрузке не падать — отключать второстепенное, сохраняя ядро.

```
Нормальная работа:        При перегрузке:
┌─────────────────┐        ┌─────────────────┐
│ ✓ Чтение статей │        │ ✓ Чтение статей │  ← никогда не отключать
│ ✓ Комментарии   │  →     │ ✗ Комментарии   │  ← отключаем
│ ✓ Рекомендации  │        │ ✗ Рекомендации  │  ← отключаем
│ ✓ Счётчики онл. │        │ ✗ Счётчики онл. │  ← кэш навсегда
│ ✓ Поиск         │        │ ✓ Поиск (TTL×10)│  ← устаревшие данные ОК
└─────────────────┘        └─────────────────┘
```

**Инструменты деградации:**
- Увеличить TTL кэша (показывать устаревшее вместо запроса в БД)
- Вернуть заглушку вместо реального блока
- Feature flags: выключатель на каждую нагруженную фичу

## 4. Очереди, микросервисы и асинхронная обработка

### 4.1 Паттерн «Очередь / Брокер сообщений»

```
┌──────────────────────────────────────────────────────────────┐
│                     QUEUE / BROKER                           │
│                                                              │
│  Producer          Queue               Consumer              │
│  ┌─────────┐      ┌────────┐          ┌──────────────┐      │
│  │ Backend │─enq─▶│ msg1   │─dequeue─▶│   Daemon 1   │      │
│  │         │      │ msg2   │          └──────────────┘      │
│  └─────────┘      │ msg3   │          ┌──────────────┐      │
│                   │ ...    │─dequeue─▶│   Daemon 2   │      │
│                   └────────┘          └──────────────┘      │
│                                                              │
│  Гарантии: at-least-once delivery, retry on failure         │
└──────────────────────────────────────────────────────────────┘
```

**Типичный flow:**
```
POST /publish-video
    ↓
Backend: save metadata to DB
Backend: queue.enqueue("transcode", {video_id: 123, format: "mp4"})
Backend: return HTTP 202 Accepted   ← пользователь НЕ ждёт
    ↓ (асинхронно, через секунды/минуты)
Daemon: dequeue → ffmpeg → upload to CDN → update DB status
```

**Виды очередей:**

| Тип | Поведение | Примеры |
|---|---|---|
| FIFO | Строгий порядок | RabbitMQ, SQS, Redis List |
| Priority Queue | Важные вперёд | Celery + priority |
| Delayed Queue | Выполнить через N секунд | SQS Delay, Redis ZSET |
| Dead Letter Queue | Неудавшиеся сообщения | Для анализа и ручного retry |

### 4.2 Паттерн «Конвейер» (Pipeline)

Задачу, слишком большую для одного воркера, разбиваем на этапы:

```
Задача: разослать письма 100M подписчиков Цукерберга

Проблема: 100M задач за раз → запись 100M записей в очередь = долго

Решение (3 этапа):

[Trigger]                [Splitter]               [Chunker]          [Sender]
"Разошли всем"  ──Q1──▶  1 задача                ──Q2──▶  1000     ──Q3──▶ Отправка
подписчикам             разбивается на            задач разбиваются         email
                        100 чанков                на 1000 подчанков
                        (по 1M каждый)            (по 1000 каждый)

Масштабируется: добавить воркеров на любом этапе
```

**Принцип**: одна большая задача → много маленьких → параллельная обработка.

### 4.3 Монолит vs Микросервисы

```
        МОНОЛИТ                           МИКРОСЕРВИСЫ
┌────────────────────┐          ┌──────┐ ┌──────┐ ┌──────┐
│                    │          │ Auth │ │Users │ │Posts │
│  Auth              │          └──┬───┘ └──┬───┘ └──┬───┘
│  Users             │             └─────────┼─────────┘
│  Posts             │                       │
│  Notifications     │          ┌────────────▼────────────┐
│  Search            │          │     Message Bus          │
│  ...               │          │  (Kafka / RabbitMQ)     │
└────────────────────┘          └──────────────────────────┘
    Один процесс                ┌──────┐ ┌──────┐
    Один деплой                 │Notif.│ │Search│
                                └──────┘ └──────┘
```

| Критерий | Монолит | Микросервисы |
|---|---|---|
| Скорость разработки | Быстрее (нет API-границ) | Медленнее (договариваться о контрактах) |
| Деплой | Всё вместе | Независимо |
| Масштабирование | Всё целиком | Каждый сервис отдельно |
| Отказоустойчивость | Один сбой = всё упало | Изолированные сбои |
| Сложность | Низкая | Высокая (distributed systems) |
| **Когда** | Стартап, 1–10 разработчиков | Зрелый продукт, много команд |

### 4.4 Межсервисное взаимодействие

**Паттерн 1: Shared Message Bus (Kafka)**
```
Service A ──publish──▶ Kafka Topic ──subscribe──▶ Service B
                                   ──subscribe──▶ Service C
                                   ──subscribe──▶ Service D
```
Плюс: простота для producer. Минус: сложнее гарантировать порядок и exactly-once.

**Паттерн 2: Transactional Outbox** (надёжнее)
```
Service A:
  BEGIN TRANSACTION
    INSERT INTO orders (...)
    INSERT INTO outbox (event="order_created", data=..., sent=false)
  COMMIT

Retry Daemon (каждые N секунд):
  SELECT * FROM outbox WHERE sent=false LIMIT 100
  FOR EACH event:
    POST /service-b/events  (с retry + exponential backoff)
    UPDATE outbox SET sent=true WHERE id=event.id
```

Outbox надёжнее: запись события атомарна вместе с бизнес-операцией. Если брокер упал — событие не потеряется.

### 4.5 Практические нюансы очередей

Очередь не делает систему автоматически надёжной. Она меняет синхронную проблему на асинхронную: пользователь не ждёт, но появляются задержки, повторная обработка, мониторинг backlog и вопросы доставки.

**Где ставить очередь:**

| Вариант | Как работает | Когда подходит | Риск |
|---|---|---|---|
| **Общая очередь-брокер** | Все сервисы пишут в один брокер/кластер | Простая интеграция, event bus | Брокер становится критичной инфраструктурой |
| **Входная очередь сервиса** | У каждого сервиса своя очередь входящих задач | Изоляция отказов между сервисами | Больше компонентов и мониторинга |
| **Выходная очередь сервиса** | Сервис сначала пишет задачу себе, потом доставляет наружу | Надёжная отправка, проще retry | Дублирование логики доставки |
| **Outbox в БД** | Событие хранится рядом с бизнес-данными | Нельзя потерять событие после COMMIT | Нужен daemon, который выгребает outbox |

**Что обязательно проектировать:**
- **Идемпотентность consumer-а**: сообщение может прийти два раза. Обработчик должен безопасно повторять операцию по `message_id`/`event_id`.
- **Retry policy**: мгновенный бесконечный retry убивает downstream. Нужны лимиты, exponential backoff, jitter.
- **Dead Letter Queue**: сообщения, которые стабильно падают, уходят в отдельную очередь для анализа, а не блокируют поток.
- **Backpressure**: если consumer не успевает, producer должен замедляться, деградировать или отказывать, иначе backlog растёт бесконечно.
- **Порядок сообщений**: глобальный порядок дорогой. Обычно достаточно порядка внутри ключа (`user_id`, `chat_id`, `order_id`).
- **Размер сообщения**: в очередь кладут ссылку/ID и метаданные, а не большие файлы. Видео и фото лежат в object storage.
- **Наблюдаемость**: длина очереди, возраст самого старого сообщения, скорость enq/deq, число retry, DLQ, lag по consumer group.

**Kafka vs классическая очередь:**

| Свойство | RabbitMQ/SQS-подход | Kafka-подход |
|---|---|---|
| Модель | Сообщение забрали → оно исчезло/ack | Сообщения лежат в append-only log |
| Основной кейс | Фоновые задачи, work queue | Поток событий, replay, много подписчиков |
| Порядок | Внутри очереди/партиции | Внутри partition |
| Replay | Обычно сложнее | Нативно: consumer хранит offset |
| Масштабирование | Добавляем consumer-ов | Добавляем partitions и consumer group |

**Сглаживание пиков:** если внезапно пришло 1M задач, очередь позволяет backend-у быстро принять работу и обработать её с постоянной скоростью. Но это работает только если бизнес допускает задержку. Если задержка недопустима, очередь не спасает — нужна синхронная мощность или деградация.

## 5. Балансировка нагрузки и отказоустойчивость

### 5.1 Уровни балансировки

```
Уровень DNS (геобалансировка):
  api.example.com → DNS → 1.2.3.4 (EU, latency 10ms)
                        → 5.6.7.8 (US, latency 150ms для EU пользователя)
  Проблема: DNS TTL делает failover медленным (30с–5мин)

Уровень L4 (TCP):
  Аппаратный LB (Cisco) или software (HAProxy)
  Маршрутизация по IP/порту, не смотрит внутрь запроса

Уровень L7 (HTTP):
  Nginx, Envoy — смотрит на URL, Cookie, заголовки
  Можно маршрутизировать /api → backend, /static → CDN
```

### 5.2 Алгоритмы балансировки

| Алгоритм | Описание | Применение |
|---|---|---|
| **Round Robin** | По очереди | Однородные серверы, короткие запросы |
| **Weighted RR** | С весами по мощности | Серверы разной мощности |
| **Least Connections** | К наименее нагруженному | Долгие соединения (WebSocket, streaming) |
| **Random** | Случайный выбор | Большое число серверов |
| **IP Hash** | Один клиент → всегда один сервер | Stateful сессии (не рекомендуется — нарушает горизонтальное масштабирование) |

### 5.3 Требования к горизонтальному масштабированию

Чтобы добавление серверов реально помогало:

1. **Stateless** — не хранить состояние между запросами локально
   ```
   ❌ Сессия в RAM backend-а → запросы привязаны к серверу
   ✓ Сессия в Redis → любой backend может ответить
   ```
2. **No SPOF (Single Point of Failure)** — дублировать каждый компонент
3. **Homogeneous** — все backend-узлы одинаковы, любой обрабатывает любой запрос

**Исключение — stateful серверы**: игровые серверы не подходят под эту модель, потому что у них количество операций чтения ≈ количеству операций записи. Каждое движение игрока сразу и читается соседями, и записывается. Репликация здесь бессмысленна — slave будет загружен как master.

### 5.4 CDN (Content Delivery Network)

```
                 Без CDN:                              С CDN:
Москва → Origin (Нью-Йорк)               Москва → Edge (Москва/Франкфурт)
         ~150ms, каждый запрос                      ~5ms, из кэша
                                                    ↓ cache miss
                                          Origin (Нью-Йорк) — один раз
```

**Что кэшировать на CDN**: статика (JS/CSS/изображения), видео, популярные API-ответы.
**Что НЕ кэшировать**: персонализированные данные, аутентификационные запросы.

**Инвалидация CDN кэша**: сложнее, чем серверный кэш. Решения:
- Версионные URL: `/static/app.abc123.js` — меняй хэш при деплое
- Короткий TTL + stale-while-revalidate
- API инвалидации (Cloudflare, Fastly)

### 5.5 Высокая доступность (High Availability)

**Active-Passive Failover:**
```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  Primary     ◀──heartbeat (ping/5s)──▶    Standby          │
│  (VIP, трафик)                          (ждёт)             │
│                                                             │
│  Если Primary не ответил 3 раза подряд (15с):              │
│    Standby берёт Virtual IP                                 │
│    Standby начинает принимать трафик                        │
│                                                             │
│  RTO ≈ 15–30 секунд                                         │
└─────────────────────────────────────────────────────────────┘
```

**Active-Active**: оба сервера принимают трафик одновременно → выше производительность, сложнее синхронизация.

### 5.6 Chaos Engineering (Chaos Monkey)

Netflix popularized: запустить процесс, который случайно убивает сервисы в production под нагрузкой.

```
Chaos Monkey:
  1. Выбирает случайный сервер
  2. Убивает случайный процесс (может попасть в БД, кэш, nginx)
  3. Система должна продолжить работу

Если система упала — значит она не готова к реальным сбоям
(а реальные сбои обязательно случатся)
```

Яндекс: в поисковом кластере сгорает ~10–20 серверов в день. Система проектируется так, чтобы это было штатной ситуацией.

## 6. Базы данных: транзакции, репликация, шардирование

### 6.1 ACID-транзакции

Четыре гарантии реляционных БД:

```
A — Atomicity (Атомарность)
    Транзакция выполняется полностью или не выполняется совсем.
    BEGIN → [5 UPDATE] → COMMIT или ROLLBACK

C — Consistency (Согласованность)
    После транзакции БД остаётся в корректном состоянии.
    Все ограничения (constraints) соблюдены.

I — Isolation (Изолированность)
    Параллельные транзакции не видят незафиксированных изменений друг друга.
    Каждая транзакция работает как будто она единственная.

D — Durability (Надёжность)
    После COMMIT данные сохранены, даже если сервер упадёт.
    Данные записаны на диск (WAL-лог).
```

**Уровни изоляции** (от слабого к строгому):
- `READ UNCOMMITTED` — видны грязные чтения (почти не используется)
- `READ COMMITTED` — видны только зафиксированные данные (дефолт PostgreSQL)
- `REPEATABLE READ` — одинаковый SELECT во время транзакции (дефолт MySQL InnoDB)
- `SERIALIZABLE` — полная изоляция, самый медленный

### 6.2 CAP-теорема

Для распределённых систем невозможно одновременно обеспечить все три свойства:

```
         Consistency (C)
         Согласованность
         /             \
        /               \
       / CA           CP  \
      /                    \
 Availability ── AP ── Partition
 Доступность        Tolerance (P)
                  Устойчивость к разделению
```

| Выбор | Примеры | Жертва |
|---|---|---|
| **CP** (Согл. + Устойч.) | HBase, Zookeeper | Доступность при сетевом разделе |
| **AP** (Дост. + Устойч.) | Cassandra, DynamoDB | Временная несогласованность |
| **CA** (Согл. + Дост.) | Традиционные RDBMS | Не работает в распределённой сети |

**На практике**: сетевые разделы случаются всегда, поэтому выбор между C и A. Интернет-сервисы чаще выбирают AP (eventual consistency).

### 6.3 Репликация Master-Slave

```
┌──────────────────────────────────────────────────────────────┐
│                   MASTER-SLAVE REPLICATION                   │
│                                                              │
│  Записи (INSERT/UPDATE/DELETE)       Чтения (SELECT)         │
│         │                                 │                  │
│         ▼                                 │                  │
│  ┌─────────────┐  replication    ┌────────┴───────┐         │
│  │   MASTER    │ ──── log ──────▶│    SLAVE 1     │         │
│  │  (Primary)  │ ──── log ──────▶│    SLAVE 2     │         │
│  └─────────────┘   async (lag!)  │    SLAVE N     │         │
│                                  └────────────────┘         │
│                                                              │
│  Типичное соотношение: 1 запись : 1000 чтений               │
└──────────────────────────────────────────────────────────────┘
```

**Проблема репликационного лага**: данные из master доходят до slave с задержкой (обычно миллисекунды, но может быть секунды).

**Решения:**

| Проблема | Решение |
|---|---|
| Пользователь только что написал, но сам не видит свой пост | Read-your-own-writes: после записи N секунд читать с master |
| Видео «счётчик лайков» скачет при чтении с разных slave | Sticky session: один пользователь → один slave |
| Банк: списание денег не отображается сразу | Показать изменение клиентски (толстый клиент вычтет из локального стейта) |

**Когда репликация НЕ помогает**: в играх, где записей не меньше, чем чтений — slave нагружен так же, как master.

### 6.4 Вертикальное шардирование (Functional Sharding)

Разные типы данных → разные СУБД, оптимизированные под задачу:

```
┌─────────────────────────────────────────────────────────────┐
│                  ВЕРТИКАЛЬНОЕ ШАРДИРОВАНИЕ                  │
│                                                             │
│  Пользователи ──▶ PostgreSQL (ACID, реляция, сложные JOIN)  │
│  Сообщения    ──▶ Cassandra  (time-series, append-only)     │
│  Сессии       ──▶ Redis      (key-value, in-memory, TTL)    │
│  Полнотекст   ──▶ Elasticsearch (инвертированный индекс)    │
│  Файлы/видео  ──▶ S3 / MinIO (object storage)              │
│  Графы связей ──▶ Neo4j      (граф-БД)                     │
└─────────────────────────────────────────────────────────────┘
```

### 6.5 Горизонтальное шардирование

Одна таблица слишком большая — делим строки по N серверам:

```
┌─────────────────────────────────────────────────────────────┐
│               ГОРИЗОНТАЛЬНОЕ ШАРДИРОВАНИЕ                   │
│                                                             │
│  Шард-ключ: user_id                                         │
│  shard_id = hash(user_id) % N                               │
│                                                             │
│  user_id=1  → shard 0 (DB Server A)  ┌──────────────────┐  │
│  user_id=2  → shard 2 (DB Server C)  │ Routing Layer    │  │
│  user_id=3  → shard 1 (DB Server B)  │ (знает где кто)  │  │
│                                      └──────────────────┘  │
│         DB A         DB B         DB C                      │
│        ┌──────┐     ┌──────┐     ┌──────┐                  │
│        │ sh 0 │     │ sh 1 │     │ sh 2 │                  │
│        │ sh 3 │     │ sh 4 │     │ sh 5 │                  │
│        └──────┘     └──────┘     └──────┘                  │
└─────────────────────────────────────────────────────────────┘
```

**Виртуальные шарды** — ключевой приём для роста без миграции:
```
Создаём сразу 1000 виртуальных шардов → раскладываем на 2 реальных сервера
Sh0-499 → Server A
Sh500-999 → Server B

При добавлении Server C:
  Перемещаем sh300-499 → Server C  (меняем только таблицу маппинга)
  Код не трогаем!
```

**Выбор шард-ключа:**
- `user_id` — хорошо: равномерное распределение
- `created_at` — плохо: все новые записи на один шард (горячий шард)
- `country` — плохо: USA >> все остальные

**Проблема горячих шардов / «знаменитостей»**:
```
Сайт знакомств: 200M пользователей, шардируем по user_id
Знаменитость с 1M просмотров/день попадает в один шард
→ один сервер под огромной нагрузкой, остальные простаивают

Решения:
1. «Золотой шард» — специальный выделенный шард для VIP-пользователей
   (мониторинг нагрузки → при превышении порога → переносим в золотой шард)

2. Таблица исключений — для VIP другой алгоритм выбора шарда

3. Репликация внутри горячего шарда — добавить slave только для него

4. Кэш поверх — анкета знаменитости почти не меняется, зашей в кэш навсегда
```

**Проблемы шардирования:**

| Проблема | Решение |
|---|---|
| JOIN между шардами | Денормализация данных |
| Запросы по нескольким шардам | Scatter-gather (параллельный запрос на все шарды) |
| Изменение шард-ключа | Почти невозможно — выбирать правильно сразу |
| Перенос шарда без downtime | Копировать → двойная запись → переключить маппинг → удалить старое |

**Два подхода к маршрутизации:**
- **Алгоритм в коде** (`hash(user_id) % N`): просто, без SPOF, но сложно менять при изменении числа шардов
- **Центральный диспетчер**: гибко менять маппинг, но SPOF и дополнительная latency

Новостной сайт: новости старше суток почти не читают

┌────────────────────────────────────────────────────────────┐
│                                                            │
│   HOT (последние 24ч)                                      │

### 6.7 Денормализация

**Нормализованная БД** → один источник правды, медленные JOIN при чтении.
**Денормализация** → хранить данные в нескольких формах, оптимизированных под чтение.

**Принцип**: *данные хранятся так, как их удобно отдавать, а не так, как удобно хранить*.

```
Нормализованно (3 таблицы, 3 JOIN):

  articles: {id, text, author_id, date}
  authors:  {id, name, avatar}
  likes:    {article_id, user_id}

Запрос на страницу статьи:
  SELECT a.*, u.name, u.avatar, COUNT(l.user_id) as likes
  FROM articles a
  JOIN authors u ON a.author_id = u.id
  LEFT JOIN likes l ON l.article_id = a.id
  WHERE a.id = 42

Денормализованно (1 запрос):

  articles_flat: {id, text, author_id, author_name, author_avatar, likes_count, date}
  SELECT * FROM articles_flat WHERE id = 42
  ← но при изменении имени автора надо обновить миллионы строк!
```

**Паттерн: одно действие = несколько записей**

Пользователь отправил сообщение → обновляем:
1. Таблицу сообщений (каноническое хранилище)
2. Поисковый индекс
3. Список последних N сообщений по каждой рубрике (денормализованный кэш)
4. Статистику (счётчики)

При удалении пользователя — рассылаем событие всем сервисам через очередь, каждый очищает своё.

### 6.8 Параллельное выполнение запросов

```
Поисковый запрос в Яндексе:

Пользователь: "highload chat design"
    ↓
Query Router
    ├──▶ Index Shard 1    ──▶ топ-10 ─┐
    ├──▶ Index Shard 2    ──▶ топ-10 ─┤
    ├──▶ Index Shard 3    ──▶ топ-10 ─┼──▶ Merger ──▶ топ-10 global → пользователю
    │    (10 000+ шардов)             │
    └──▶ Index Shard N    ──▶ топ-10 ─┘
    
Одновременно:
    ├──▶ Реклама (parallel)
    ├──▶ Картинки (parallel)
    └──▶ Видео (parallel)
```

Итог склеивается из всех параллельных ответов. Весь запрос — ~50ms, хотя данных петабайты.

### 6.9 Comet-сервер / Push-сервер (реальное время)

```
┌─────────────────────────────────────────────────────────────┐
│                   PUSH-СЕРВЕР ДЛЯ ЧАТА                      │
│                                                             │
│   Alice ──WS──▶ Push Server                                 │
│                      │  pub-sub                             │
│                 Channel "chat:42"  ──▶ Bob (WS)             │
│                      │             ──▶ Carol (WS)           │
│                      │             ──▶ Dave (WS)            │
│                                                             │
│   Alice отправляет сообщение:                               │
│   1. WS → Push Server                                       │
│   2. Backend сохраняет в БД                                 │
│   3. publish("chat:42", message)                            │
│   4. Все подписчики канала получают push                    │
└─────────────────────────────────────────────────────────────┘
```

**Особенности:**
- Тысячи долгоживущих соединений на один сервер → stateful
- Pub-sub брокер: Redis Pub/Sub, Kafka (для горизонтального масштабирования push-серверов)
- Специализированный ПО для долгих соединений: nginx с `push_stream_module`, Centrifugo, Pusher

### 6.10 Индексы в базах данных

Индекс — отдельная структура данных, которая ускоряет поиск строк, но замедляет запись. При `INSERT/UPDATE/DELETE` БД должна изменить не только таблицу, но и все затронутые индексы.

**Базовая идея:**

```
Без индекса:
  SELECT * FROM users WHERE email='a@b.com'
  → full table scan: проверить все строки

С индексом:
  CREATE INDEX users_email_idx ON users(email)
  → index lookup: найти email в дереве → перейти к строке
```

**Главный компромисс:** индекс ускоряет чтение и фильтрацию, но стоит места на диске, памяти в buffer cache и времени на запись.

| Тип индекса | Для чего | Пример |
|---|---|---|
| **B-tree** | Равенство, диапазоны, сортировка | `WHERE user_id = 42`, `created_at > now()-interval '1 day'` |
| **Hash** | Только равенство | `WHERE token = '...'` |
| **GIN** | Массивы, JSONB, полнотекст | `tags @> ['java']`, `jsonb ? 'key'` |
| **GiST/SP-GiST** | Геоданные, интервалы, nearest-neighbor | координаты, bounding box |
| **Partial index** | Индекс только на часть строк | `WHERE status = 'active'` |
| **Composite index** | Несколько колонок в одном индексе | `(user_id, created_at)` |
| **Covering index** | Индекс содержит всё для запроса | `INCLUDE (title, status)` |

**Селективность и кардинальность:**
- **Высокая селективность**: условие оставляет мало строк (`email`, `user_id`) — индекс полезен.
- **Низкая селективность**: условие оставляет много строк (`gender`, `is_active`) — БД может выбрать full scan.
- **Кардинальность**: количество разных значений в колонке. Чем больше разных значений, тем чаще индекс полезен.

**Составной индекс и порядок колонок:**

```
CREATE INDEX posts_user_created_idx ON posts(user_id, created_at DESC);

Хорошо:
  WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20
  WHERE user_id = 42 AND created_at > '2026-01-01'

Плохо:
  WHERE created_at > '2026-01-01'
```

B-tree индекс эффективно используется слева направо. Если индекс `(user_id, created_at)`, то запрос только по `created_at` обычно не использует его как основной путь.

**Практические правила:**
- Индексируй поля, по которым часто фильтруют, сортируют или соединяют таблицы (`WHERE`, `ORDER BY`, `JOIN ON`).
- Для ленты обычно нужен индекс вида `(owner_id, created_at DESC)`, а не два отдельных индекса.
- Для `LIMIT` индекс особенно важен: БД может взять первые N строк в нужном порядке, не сортируя всю таблицу.
- Не индексируй каждую колонку «на всякий случай»: запись станет медленнее, а planner всё равно выберет только часть индексов.
- Индекс на маленькой таблице часто не нужен: full scan дешевле.
- Если запрос возвращает значительную часть таблицы, индекс может проиграть последовательному чтению.

**EXPLAIN — обязательная проверка:**

```
EXPLAIN ANALYZE
SELECT *
FROM posts
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

Смотри:
- `Seq Scan` — полный проход по таблице. Нормально для маленьких таблиц, подозрительно для больших.
- `Index Scan` / `Index Only Scan` — используется индекс.
- `Rows Removed by Filter` — много лишних строк прочитано и отброшено.
- `Sort` на большом наборе — возможно, нужен индекс под порядок сортировки.
- `actual time` и `rows` — реальные цифры, а не догадки.

**Индекс vs денормализация vs шардирование:**
- Сначала проверь запрос и индекс. Часто один правильный индекс дешевле новой архитектуры.
- Если JOIN медленные даже с индексами — думай о денормализации.
- Если индекс/таблица не влезают на одну машину или hot set больше памяти — думай о партиционировании и шардировании.
- Если запрос требует поиск по всему интернету/каталогу — нужен специализированный поисковый индекс, а не обычный B-tree.

ШАГ 4. Допустимая деградация

### 7.3 Практический пример: Спортивная текстовая трансляция

**Входные данные:**
- 100 000–200 000 зрителей одновременно
- 2 ведущих пишут ~5 сообщений/мин
- 200 000 зрителей пишут ~100 комментариев/мин
- Задержка до 10 секунд — допустима
- Сообщения одинаковы для всех (нет персонализации)
- Хранить историю ленты ведущих навсегда, комментарии — только последние ~1000

**Оценка нагрузки:**
```
Зрители polling каждые 10с → 200 000 / 10 = 20 000 RPS
Объём сообщения ≈ 100 байт → 20 000 × 100 = 2 MB/s исходящего трафика
```

**Ключевая особенность данных**: все получают одно и то же → нет персонализации → можно кэшировать агрессивно.

**Архитектурное решение:**

```
                  ВАРИАНТ 1 (Рекомендуется для задержки ≤10с)

Редакторы
  │
  ▼ POST /add-message
Backend ──▶ Сохранить в БД
        ──▶ Сгенерировать JSON файл: /feed.json
                │
                ▼
         Nginx (cache TTL=5–10с)
                │
                ▼ (отвечает 20 000 RPS из кэша, backend получает ~0 RPS)
         200 000 зрителей (polling каждые 10с)

Пользовательские комментарии:
  Все пишут в очередь → 1 daemon пробуждается раз в 5с, сортирует,
  обновляет /comments.json → нет race condition с параллельной записью

Фотографии: CDN (origin = backend, edge = ближайший к зрителю)

История (архив матчей): chunked JSON files
  /match/42/events_1.json, events_2.json, ...
  При первом GET клиент узнаёт номер последнего чанка → скачивает недостающие
```

```
                  ВАРИАНТ 2 (Если нужна задержка ≤1с)

Backend ──publish──▶ Comet Server ──WebSocket──▶ 200 000 зрителей

Сложнее: нужен специализированный push-сервер,
  горизонтальное масштабирование через Redis Pub/Sub,
  управление 200k постоянных соединений
```

**Вывод**: задержка 10с → вариант 1 (статический файл + кэш) проще, надёжнее, масштабируемее. Comet нужен только для real-time (<1с).

### 7.4 Практический пример: Сайт знакомств (Profile Service)

**Входные данные:**
- 200M пользователей, рост медленный
- 5B просмотров профилей в день → ~57 000 RPS
- Средний размер анкеты ≈ 10 KB → 10 KB × 57 000 = 570 MB/s исходящего трафика
- Редактирование профиля: раз в месяц → ~77 RPS записи
- Деградация недопустима (99.9% uptime)
- Есть «знаменитости» с миллионами просмотров/день

**Расчёт хранилища:**
```
200M пользователей × 10 KB = 2 TB данных
→ не влезает на одну машину → нужно шардирование
```

**Архитектура:**
```
1. Горизонтальное шардирование по user_id
   Виртуальные шарды (1000 штук) → маппинг на реальные серверы

2. Репликация внутри каждого шарда
   Master + 2 Slave → отказоустойчивость + читаем со slave

3. «Золотой шард» для знаменитостей
   Мониторинг нагрузки → если RPS на профиль > порога →
   переносим в спецшард с отдельными настройками и репликой×3

4. Кэш for hot profiles
   Знаменитость меняет профиль редко → кэш TTL=1h достаточен
   Обычный профиль: 25 просмотров/сутки → кэш бессмысленен (вымоется)
```

| **Push Server (Comet)** | Polling неэффективен | Постоянные соединения + pub-sub | Stateful, сложнее масштабировать |

### 9.4 Правило «читается в 100× чаще, чем пишется»

Типичный интернет-сервис: на 1 запись приходится ~100–1000 чтений.

Следствие: кэшировать выгодно, репликация (больше slave) эффективна, денормализация оправдана.

**Исключения** (записей ≈ чтений):
- Игровые серверы (позиции игроков)
- Биржевые терминалы
- IoT / телеметрия в реальном времени

Для этих случаев репликация не помогает — нужно другое решение (stateful серверы, специализированные time-series БД).

## 10. Практика: реальные проблемы highload-систем

Паттерны из лекций обычно проявляются в проде не как красивые схемы, а как симптомы: вырос p99, очередь не разгребается, кэш внезапно перестал помогать, replica lag сломал UX, один celebrity-profile положил шард.

### 10.1 Как разбирать проблему

```
Симптом → Метрика → Узкое место → Гипотеза → Маленькое изменение → Проверка
```

**Не начинать с решения.** Сначала понять, что именно закончилось: CPU, память, диск, сеть, connections, lock-и, лимит downstream-сервиса, пропускная способность очереди или свежесть данных.

| Симптом | Что смотреть первым | Частая причина |
|---|---|---|
| p95/p99 latency вырос, среднее нормальное | percentiles, slow requests, tracing | Длинный хвост: редкие медленные зависимости |
| CPU backend-а 100% | CPU profile, RPS, flamegraph | Тяжёлая бизнес-логика, JSON, regex, N+1 |
| БД медленная | slow query log, `EXPLAIN ANALYZE`, locks | Нет индекса, плохой план, блокировки |
| Очередь растёт | enq/deq rate, oldest message age | Consumer медленнее producer-а |
| Пользователь не видит свою запись | replica lag, routing чтения | Чтение ушло на slave до репликации |
| Всплеск ошибок после сбоя downstream | retry count, outgoing RPS | Retry storm |
| Один сервер перегружен, остальные нет | распределение ключей/шардов | Hot key / hot shard |

### 10.2 Tail latency: почему среднее врёт

Если 99 запросов отвечают за 20 ms, а один — за 2 s, среднее выглядит терпимо, но каждый сотый пользователь видит плохой UX. В highload важнее смотреть не только average, а p50/p95/p99.

```
100 запросов:
  99 × 20 ms
   1 × 2000 ms

average ≈ 40 ms
p99 = 2000 ms
```

**Почему появляется длинный хвост:**
- один shard перегружен;
- один downstream иногда тормозит;
- garbage collection / stop-the-world pause;
- холодный кэш;
- lock contention в БД;
- сетевые retransmit-ы;
- большие ответы вытесняют маленькие.

**Что помогает:**
- timeout budget на каждый downstream;
- parallel requests с ограничением concurrency;
- hedged requests для read-only операций;
- кэширование горячих данных;
- разделение тяжёлых и лёгких запросов по очередям/пулам;
- отдельные лимиты для batch/background задач.

### 10.3 Retry storm

Retry нужен для временных ошибок, но без ограничений он сам становится атакой на систему.

```
Service A → Service B
Service B начал отвечать 500
Service A делает 3 retry без задержки

Итог:
  было 10 000 RPS
  стало до 40 000 RPS на Service B
  B восстанавливался бы, но retry добивает его окончательно
```

**Правильный retry:**
- только для безопасных/idempotent операций;
- exponential backoff;
- jitter, чтобы клиенты не повторяли одновременно;
- ограничение числа попыток;
- circuit breaker, если downstream явно лежит;
- отдельный retry через очередь для долгих операций.

**Анти-паттерн:** retry внутри каждого слоя. Клиент делает 3 попытки, API делает 3 попытки, worker делает 3 попытки — downstream получает 27 запросов на одну пользовательскую операцию.

### 10.4 Connection pool exhaustion

Частая проблема: БД сама не на 100% CPU, но приложение зависает, потому что закончились соединения в пуле.

```
Backend pool: 100 connections
Каждый запрос держит connection 500 ms
Максимальная пропускная способность ≈ 100 / 0.5 = 200 RPS

При 1000 RPS:
  200 RPS реально работают
  800 RPS ждут connection
  latency растёт, user timeout, retry, ещё больше нагрузки
```

**Что делать:**
- держать транзакции короткими;
- не делать HTTP-вызовы внутри DB-транзакции;
- ограничивать concurrency на уровне приложения;
- разделять read/write pools;
- ставить timeout ожидания connection;
- измерять `pool_wait_time`, а не только latency SQL.

### 10.5 N+1 запросы

Типичный скрытый убийца БД.

```
GET /feed
  SELECT * FROM posts LIMIT 50
  FOR EACH post:
    SELECT * FROM users WHERE id = post.author_id
    SELECT count(*) FROM likes WHERE post_id = post.id

Итог: 1 + 50 + 50 = 101 SQL-запрос на один HTTP-запрос
```

При 1000 RPS это уже 101 000 QPS к БД.

**Решения:**
- JOIN или batch-запросы (`WHERE id IN (...)`);
- предрасчитанные счётчики;
- денормализованные поля (`author_name`, `likes_count`);
- DataLoader-подход: собрать все нужные ключи и сходить одним запросом;
- кэширование справочников и профилей авторов.

### 10.6 Hot key и hot shard

Средняя нагрузка может быть нормальной, но один ключ ломает систему.

```
200M профилей
Средний профиль: 25 просмотров/день
Профиль знаменитости: 5M просмотров/день

Шардирование по user_id распределило пользователей равномерно,
но нагрузку распределило неравномерно.
```

**Симптомы:**
- один shard/partition горячий;
- один Redis key получает непропорционально много QPS;
- latency скачет только для части пользователей;
- общий RPS нормальный, но p99 плохой.

**Решения:**
- отдельный golden shard для горячих объектов;
- репликация только горячего shard-а;
- кэширование hot key с большим TTL;
- key splitting: `profile:vip:1:part:N`;
- precompute/read-optimized копия;
- ручная таблица исключений для VIP/celebrity.

### 10.7 Проблемы кэша в проде

Кэш ускоряет систему, но создаёт новые классы отказов.

| Проблема | Как выглядит | Что делать |
|---|---|---|
| Cache stampede | TTL истёк, все пошли в БД | Lock на пересчёт, stale-while-revalidate, random TTL |
| Cold cache after deploy | После рестарта всё медленно | Warm-up популярных ключей |
| Stale data | Пользователь видит старое | Явная инвалидация, version tags, короткий TTL |
| Hot key | Один ключ грузит Redis/сеть | Local cache, key splitting, read replicas |
| Cache penetration | Запрашивают несуществующие ключи | Negative cache, bloom filter, rate limit |
| Big value | Один ключ занимает MB | Резать объект, хранить ссылку, compress осторожно |

**Опасный сигнал:** система «работает только с прогретым кэшем». Если БД умирает при пустом кэше, деплой или сброс Redis становится инцидентом.

### 10.8 Queue backlog и poison message

Очередь сглаживает пики, но если входной поток долго больше выходного, backlog растёт без ограничений.

```
Producer: 50 000 msg/s
Consumer: 30 000 msg/s
Backlog растёт на 20 000 msg/s

За 10 минут:
  20 000 × 600 = 12M сообщений долга
```

**Что смотреть:**
- скорость записи в очередь;
- скорость чтения;
- возраст самого старого сообщения;
- retry rate;
- DLQ;
- lag по partition/consumer group.

**Poison message:** одно сообщение всегда падает и возвращается в начало очереди. В плохой реализации оно блокирует всё за ним.

**Решения:**
- лимит retry;
- DLQ после N попыток;
- idempotent consumer;
- отдельные очереди для разных классов задач;
- autoscaling consumer-ов по backlog/lag;
- backpressure на producer-а.

### 10.9 Репликационный лаг и read-your-own-writes

Пользователь создал пост, backend записал в master, но следующий GET ушёл на slave, куда запись ещё не доехала.

```
T=0 ms:  INSERT post → master
T=20 ms: HTTP 200 пользователю
T=50 ms: пользователь обновляет страницу
T=60 ms: SELECT идёт на slave
T=500 ms: запись только доехала до slave

Итог: пользователь "потерял" свой пост на 440 ms
```

**Решения:**
- после записи N секунд читать этого пользователя с master;
- sticky session к одной replica;
- client-side optimistic update;
- показывать статус "сохраняется";
- для критичных данных использовать sync replication или читать из leader-а.

**Важно:** lag надо измерять и выводить в метрики. "Обычно 10 ms" не помогает, когда во время нагрузки lag становится 30 секунд.

### 10.10 Блокировки и долгие транзакции

Даже правильный индекс не спасёт, если запрос ждёт lock.

```
Transaction A:
  BEGIN
  UPDATE accounts SET balance = balance - 100 WHERE id = 1
  ... долгий HTTP-запрос наружу ...
  COMMIT

Transaction B:
  UPDATE accounts SET balance = balance + 100 WHERE id = 1
  -- ждёт lock, хотя БД "быстрая"
```

**Правила:**
- не держать транзакцию во время сетевых вызовов;
- обновлять строки в одинаковом порядке, чтобы снижать deadlock-и;
- ставить lock timeout;
- выносить тяжёлую обработку после COMMIT;
- читать lock wait metrics;
- проверять долгие idle-in-transaction сессии.

### 10.11 CDN и инвалидация

CDN отлично снимает нагрузку, пока не надо быстро удалить или обновить объект.

**Типовые проблемы:**
- пользователь сменил аватар, а CDN ещё час отдаёт старый;
- удалённый приватный файл продолжает лежать на edge;
- одинаковый URL используется для разных версий контента;
- purge API медленный или rate-limited.

**Решения:**
- content-addressed URLs: `/avatar/hash.jpg`;
- version query/path: `/static/app.v123.js`;
- короткий TTL для приватных/часто меняющихся данных;
- явный purge только для редких критичных случаев;
- разделять public static и private media.

### 10.12 Миграции без downtime

На маленькой БД можно сделать `ALTER TABLE` и подождать. На большой таблице это может заблокировать запись или переписать терабайты.

**Безопасный паттерн expand-contract:**

```
1. Expand: добавить новую колонку/таблицу, совместимую со старым кодом
2. Dual write: новый код пишет и в старую, и в новую схему
3. Backfill: фоново перелить старые данные маленькими батчами
4. Switch read: чтение переключить на новую схему
5. Contract: удалить старую колонку/таблицу после проверки
```

**Правила:**
- миграции должны быть обратимыми или хотя бы останавливаемыми;
- backfill идёт батчами с паузами и лимитом нагрузки;
- перед удалением старого поля проверить, что никто его не читает;
- большие индексы создавать online/concurrently, если СУБД поддерживает;
- rollout делать постепенно.

### 10.13 Наблюдаемость: что должно быть видно

Highload-систему нельзя поддерживать без метрик. Если нет наблюдаемости, архитектурные паттерны превращаются в гадание.

**Минимальный набор:**

| Компонент | Метрики |
|---|---|
| HTTP/API | RPS, error rate, p50/p95/p99 latency, размер ответа |
| Backend | CPU, memory, GC pauses, thread/worker pool, connection pool wait |
| БД | QPS, slow queries, locks, replication lag, cache hit ratio |
| Redis/cache | hit ratio, evictions, hot keys, memory, latency |
| Очереди | backlog, oldest message age, enq/deq rate, retries, DLQ |
| Load balancer | active connections, 4xx/5xx, upstream health |
| CDN | hit ratio, origin requests, purge latency |

**Три вопроса для dashboard-а:**
1. Пользователю сейчас плохо?
2. Какой компонент виноват?
3. Это нагрузка, отказ или ошибка релиза?

### 10.14 Мини-чеклист перед запуском highload-фичи

- Есть оценка среднего и пикового RPS.
- Есть оценка объёма данных и роста за год.
- Самая частая операция оптимизирована отдельно.
- Есть индексы под реальные запросы, проверенные через `EXPLAIN ANALYZE`.
- Есть timeout-ы на все сетевые вызовы.
- Retry ограничены и имеют backoff + jitter.
- Операции, которые могут повториться, idempotent.
- Есть rate limit и backpressure.
- Есть план деградации: что отключаем первым.
- Очереди имеют DLQ и мониторинг возраста сообщений.
- Кэш имеет стратегию инвалидации и защиты от stampede.
- Репликационный лаг измеряется, UX учитывает eventual consistency.
- Нет единой точки отказа на критическом пути.
- Миграции БД можно выполнить без долгой блокировки.
- Есть алерты по p95/p99, error rate, saturation и backlog.
